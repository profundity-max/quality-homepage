# 备份与恢复可验证性修复规格

## 背景

管理后台虽然提供“立即执行手动备份”，但缺少部署配置时只能报错；旧实现还可能在未导出数据库的情况下生成极小的加密包并记录成功。恢复脚本只解包文件，不能证明 PostgreSQL 数据可恢复。

## 验收标准

1. 完整备份必须同时包含非空 `database.dump` 和受控数据目录中的上传文件；数据库导出缺失、为空或失败时记录失败原因，不得显示成功。
2. 管理后台明确展示缺失配置、备份目录和操作结果；配置不完整时禁用手工备份。成功记录可以校验校验和、解密口令与 `database.dump` 是否存在。
3. Compose 的 Web 与运维备份容器必须获得相同的备份口令和目录，并在写入前完成数据目录及备份目录初始化；运行镜像必须包含 PostgreSQL 客户端工具。
4. `scripts/restore.ts --drill` 必须把备份中的数据库转储恢复到自动创建的隔离 PostgreSQL 数据库，核对账号、文章、书目、模板和上传文件数量，并在成功或失败后删除临时数据库、记录审计事件。
5. 自动化验证必须覆盖模块级完整包、错误路径、Compose 配置契约以及真实容器中的备份—隔离恢复闭环。
6. 密钥只通过部署环境配置，不提交到 Git；恢复演练不得覆盖生产数据库。
7. 管理员可以从备份记录下载对应的原始加密包；下载必须再次校验管理员身份，且不得暴露服务器文件系统路径。
8. 每条成功备份在管理后台提供“恢复演练”操作。该操作只恢复到自动创建的隔离 PostgreSQL 数据库，展示核对数量并记录审计；不提供网页内覆盖生产数据库的操作。
