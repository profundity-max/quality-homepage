# 版本管理与变更记录

> 状态：生效中（V2.5 起）
> 配套文件：[Q-Nexus项目变更说明.xlsx](../Q-Nexus项目变更说明.xlsx)（项目目录下的变更说明表）、仓库根目录 `VERSION`

## 规则

1. **Superpower 需求升主版本**：所有 @Superpower 需求（由技能驱动，如 `/improve-codebase-architecture`、`/implement`、`/code-review`）完成后必须升主版本号，例如 V1.0 → V2.0，并写明该版本的变更摘要与验收证据。
2. **小型修改升小版本**：用户直接要求的小型修改（缺陷修复、文案或布局调整等）按 V1.1 → V1.2 递增后缀，同样写明变更摘要。
3. **每次变更附变更说明表**：项目目录下的 `Q-Nexus项目变更说明.xlsx` 必须为每次变更追加一行，字段：版本号、日期、变更类型（Superpower 需求／小型修改／数据变更／环境变更／交付里程碑）、变更摘要、关联提交、验收证据。
4. **代码同步 Git 并可回溯**：所有代码变更提交到当前分支并推送 GitHub；每个版本打对应标签（`v1.0`、`v1.1`、`v2.0`…），保证任意版本可完整回溯。
5. **版本号落文件**：仓库根目录 `VERSION` 保存当前版本号，与 Git 标签、变更说明表保持一致。

## 每次变更的操作清单

本次未在开发电脑执行正式部署。目标机器升级前请备份数据库与受控文件，并按 [新人路线升级说明](deployment.md#v30-新人路线升级) 在备份副本验证迁移。

1. 判定类型：Superpower 需求 → 主版本 +1；直接小型修改 → 小版本 +1；纯数据/环境变更沿用当前版本号并在类型列注明。
2. 更新 `VERSION`。
3. 在 `Q-Nexus项目变更说明.xlsx`「版本总览」追加一行，必要时在「提交对照」补充提交记录。
4. 提交并推送代码。
5. 为该版本打标签并推送：`git tag v<版本> && git push origin v<版本>`（网络受限时可用 GitHub API 创建同名标签）。
