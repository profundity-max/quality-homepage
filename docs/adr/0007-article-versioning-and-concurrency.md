# 文章版本采用快照表与乐观并发控制

## 状态

已接受（Slice 3 生效）

## 背景

VER-01/02/03 要求：修改已发布文章时当前版本继续对阅读者可见（保存到独立草稿）、再次发布生成新版本、恢复历史版本必须填写原因并留痕。EDIT-07 要求两个编辑者同时修改不得静默覆盖。

## 决策

- **单行工作区 + 版本快照表**：articles 表承载"当前工作内容 + 状态"（draft/published/archived）；article_versions 表保存每次发布/恢复的快照（标题、摘要、正文、主题、标签、负责人、复核日期），`kind` 区分 publish/restore，restore 行必有原因（DB 条件 CHECK 强制）。
- **beginEdit 快照语义**：修改已发布文章时，先把当前已发布内容快照进历史（kind=publish），文章转为草稿；阅读侧在编辑期间返回最后发布版本（`editingInProgress` 标记），满足"阅读者继续看到旧发布版本"。
- **乐观并发（EDIT-07）**：saveDraft 携带 `expectedUpdatedAt`，与服务器 `updated_at` 不符即拒绝并提示冲突；客户端提供"保留我的版本 / 保留服务器版本"的人工选择。
- **编辑占用（EDIT-09，基础标记）**：articles 表 `editing_by`/`editing_at` 记录占用者；他人打开只读，明确确认后接管。第一版不实现心跳续期与超时自动释放（评审确认的基础方案）。

## 后果

- 每次发布都有版本行，历史完整可恢复；恢复原因与操作者留痕（VER-03）。
- 编辑期间阅读者始终可见最后发布版本，不会出现 404 空窗。
- 并发编辑不会静默覆盖；冲突时人工决策（EDIT-07）。
- 代价：单行模型下"已发布版本"是快照而非独立行，历史版本与当前内容的关联靠版本表；并发发布（max+1）无事务锁，单编辑者场景可接受，多人同时发布需评估升级。
